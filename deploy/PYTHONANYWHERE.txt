3. CREATE EXTERNAL CONFIG (not a .env in Git)
python3.13 - <<'PY'
import json, os, secrets
from pathlib import Path
home = Path.home()
hostname = input('Exact PythonAnywhere Web tab hostname: ').strip()
path = home / '.config/silent-space/staging.json'
with path.open('x') as f:
    json.dump({'hostname': hostname, 'secret_key': secrets.token_urlsafe(64),
               'data_dir': str(home / 'silent-space-data')}, f, indent=2)
os.chmod(path, 0o600)
print('Created', path)
PY

Keep this secret/config unchanged across releases. The example JSON is a schema
only and its placeholder secret is rejected. Back it up privately. The database,
uploads and email captures stay in silent-space-data, outside all Git worktrees.
Never copy the customer database or real receiving-account details into staging.

4. SELECT AND PREPARE A GREEN COMMIT
First deployment has no serving app. On subsequent releases put the app into
maintenance BEFORE confirming the flag (instructions below). Stop any manually
running notification command too. Check free disk quota for dependencies/backups.

export STAGING_CONFIG="$HOME/.config/silent-space/staging.json"
export DJANGO_SETTINGS_MODULE=silent_space.settings_staging
read -r -p 'Full successful main CI SHA: ' RELEASE_SHA
python3.13 "$HOME/silent-space-source/deploy/release.py" \
  --commit "$RELEASE_SHA" \
  --repo "$HOME/silent-space-source" \
  --root "$HOME/silent-space" \
  --venv "$HOME/.virtualenvs/silent-space" \
  --config "$STAGING_CONFIG" \
  --maintenance-confirmed

The script verifies the latest matching GitHub CI main-push run, fetches main,
checks the SHA belongs to main, creates a detached releases/SHA worktree, backs
up SQLite using its backup API and integrity check, installs dependencies into
the configured venv, checks migration drift, migrates and collects static.
Only after success does current switch atomically to the new release. It never
reloads the Web app. Inspect the printed backup/previous-release information.
Invalid SHA, failed/pending/missing CI, dirty clone, occupied release lock or an
existing target worktree stop the release. Inspect failed worktrees rather than
overwriting them or rerunning migrations blindly. Keep maintenance active on error.

8. MAINTENANCE, ERRORS AND ROLLBACK
Before later releases, save the working Web-tab WSGI text privately. Temporarily
replace it with the following and click Reload; verify HTTP 503 before releasing:

def application(environ, start_response):
    start_response('503 Service Unavailable', [('Content-Type', 'text/plain'), ('Retry-After', '300')])
    return [b'Staging maintenance; please retry shortly.']

After a successful release restore the staging WSGI loader, Reload and smoke-test.
If a release fails, keep maintenance active. Although current changes only after
success, migrations and virtualenv packages may already have changed. No automatic
database rollback is safe. The external release-<timestamp>.json manifest records
the previous release and pre-migration backup; the script also prints them.

For code rollback, choose a retained prior release, reinstall its requirements
into the same venv, verify compatibility with the CURRENT schema, and switch the
current symlink atomically. Example, after reviewing the chosen path:

export PREVIOUS_RELEASE=/home/YOUR_USERNAME/silent-space/releases/PREVIOUS_FULL_SHA
"$HOME/.virtualenvs/silent-space/bin/python" -m pip install -r "$PREVIOUS_RELEASE/requirements.txt"
python3.13 - <<'PY'
import os
from pathlib import Path
root = Path.home() / 'silent-space'
previous = Path(os.environ['PREVIOUS_RELEASE']).resolve()
assert previous.is_relative_to((root / 'releases').resolve()) and (previous / 'manage.py').is_file()
pending = root / 'rollback.next'
pending.symlink_to(previous, target_is_directory=True)
os.replace(pending, root / 'current')
PY

If schema compatibility fails, use reviewed reverse migrations or restore the
matching pre-release SQLite backup only after accepting loss of newer staging
writes. Back up the current DB first, stop all writers and restore via SQLite's
backup API (do not copy over an active WAL database). Media/secrets are external:
never remove them during rollback, and retain independent media/config backups.
Restore WSGI, Reload, and recheck private links/static/media. Do not overwrite an
existing worktree with the release command as a rollback shortcut.
